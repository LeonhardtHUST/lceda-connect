## 真机测试

机器上的客户端版本为 V4.1.78。开始时停在开始页，因此先用工程入口与 `getProjectInfo` 双重核对名称和 UUID，再打开授权工程。

| 对象             | UUID                               |
| ---------------- | ---------------------------------- |
| agent-drill-rc50 | `eb9fbbc911a7432189e71aefcbb0ff69` |
| PCB1             | `1df2fdad9f776448`                 |
| 测试原理图 P1    | `6f1f9b1bd0cbeccc`                 |

执行了以下检查：

1. Bridge 与 CDP 独立读取工程和活动文档身份，结果一致。
2. 读取 PCB 计数、板指纹、DRC，验证文档列表与激活后的焦点回读。
3. 切到指定 P1，创建唯一标记文本并按返回 ID 回读内容，再只删除该 ID。
4. 原理图文本 ID 集合恢复：前后都是 1 个，唯一测试标记残留为零。
5. 恢复 PCB1，比较板状态与指纹。
6. 截图后启动真实 MCP stdio 子进程，列出 51 个无重名工具，实际调用 `lceda_info`、`api_search`、`eda_doc_info`、`eda_read_board`，均未返回 `isError`。

成功测试的文本 ID 为 `a7dbedb3651e9fdd`，已删除。PCB 前后均为 6 个元件、66 条线、39 个过孔、2 个铺铜；`details_hash` 均为 `9fd8e3097f3c9951`，`silk_hash` 均为 `88e2f8d73c27e8c0`，`drc_leaf_hash` 均为 `464ad5cf42072316`。

DRC 前后都是 9 项（5 项间距、4 项连接），属于测试前已有状态，不代表这块板通过 DRC。读数同时提示 4 个叶子缺少完整身份字段，原警告被保留，没有把它们静默合并。

首轮载荷在返回结果时缺少 `marker` 局部变量；异常后的残留检查为零，PCB 已恢复。修复时把载荷提取为纯函数，并增加 7 个离线测试，覆盖身份错误、marker 转义、回读失败清理、删除失败与用户切换文档。随后真机重跑成功。

本次没有调用显式保存 API，也没有清空撤销历史。客户端自身的自动保存、编辑历史和更新日期可能随创建/删除及文档切换发生变化，不能把图元状态恢复理解为工程文件逐字节未变。

证据：

- `docs/reports/agent-drill-rc50-live.json`：成功执行的身份、文本往返、零残留、PCB 前后状态与 MCP 调用。
- `out/live/agent-drill-rc50-pcb.png`：恢复 PCB 后的截图（运行产物，未提交）。
- `out/live/agent-drill-rc50-first-attempt.json`：首轮失败及清理证据（运行产物，未提交）。

这轮没有对运行中的 bridge 守护进程执行重启或替换。真实写入通过当前实例的 bridge 完成，CDP 同时用于身份核对、切文档、焦点回读和截图。内置 bridge 服务仍有 HTTP/WS 集成测试覆盖，但不把这轮结果说成新内置服务与真实扩展之间的端到端证明。

## 复现

此开发脚本在 Node 26 上运行，默认不写入编辑器。每次先从 `bridge windows` 获取当前窗口 ID，不缓存旧 ID。写入模式必须显式传 `--confirm`，并固定核对本次授权的工程、PCB、原理图 UUID。

```powershell
pnpm run build
node dist/cli.mjs bridge windows --json
node scripts/live-smoke.mjs --project agent-drill-rc50 --project-uuid eb9fbbc911a7432189e71aefcbb0ff69 --window CURRENT_WINDOW_ID --schematic 6f1f9b1bd0cbeccc --confirm --out out/live/recheck.json
```
