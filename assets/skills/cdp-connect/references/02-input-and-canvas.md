## 输入与器件库：踩过的坑

### 文本输入的硬规则

实测教训：搜索框原值为 `10k`，我又 `insertText("10k")`，结果变成 `10k10k`，后面所有行坐标、结果集全部错位，排查了很久才发现根因。

固定流程，四步缺一不可：

1. **定位输入框要限定容器**。同一页面有多个 `placeholder*=搜索` 的输入框（底部「器件」面板一个、弹窗里一个），全局 `document.querySelector` 会抓到错的那个。
2. **点进输入框**，确认焦点。
3. **`Ctrl+A` 全选**（`modifiers: 2`），再 `Input.insertText`，不要直接追加。
4. **回读校验**：`el.value` 必须等于期望值，否则中止，不要带着错误输入继续。

### 器件/复用模块对话框

快捷键 `Shift+F` 打开，尺寸 1251×667，四个标签：

| 标签 | 性质 | 实测 |
|---|---|---|
| 立创商城 | 在线商城目录 | 搜 `10k` 命中 3 万+，需等 4—8 秒加载；加载完可用下方价格/库存/销量等筛选。**可用，只是慢** |
| 嘉立创EDA | 本地/系统库 | 系统 5153 件，切换后立即有数据 |
| 复用模块 | 工程内复用模块 | 未测 |
| 申请新元件 | 建库申请 | 未测 |

左侧筛选：系统 / 最近 / 个人 / 工程 / 收藏 / 团队名 / 公开 / 标准版公开。

### 放置按钮的行为

结果表的「放置」按钮**只在行悬停时出现在行右侧**，不悬停就查不到。所以放置流程是：

1. 鼠标移到目标行
2. 同一帧内立刻查「放置」按钮
3. 点它，弹窗自动关闭，元件跟随光标
4. 移到画布点击落下

注意：页面里其它虚拟列表（如底部器件表）也有大量「放置」按钮，`y` 值可能远在视口外（实测出现 y=984、1984…）。必须用**视口内 + 与目标行 y 差 < 30** 双条件筛选。

### 当前卡点

嘉立创EDA 标签下搜索 `10k` 已有数据（系统 5153 件），但按「单行高度 18—40、左边界 > 250」筛不出行，说明该表的行结构与商城标签不同。

下一步不再盲试：**先完整 dump 一次表格容器的 DOM 结构**（类名、行列层级、单元格文本分布），据此写一个稳定的行读取器，再继续放置。这也正是通用能力里 C2 的要求——先理解结构，再定位元素。

## 画布放置：最小闭环打通

### 结论

「放一个元件」可行，路径是**菜单 → 子菜单 → 画布坐标点击**，并且属性面板能回读到元件，满足 C5（校验）。

### 实测路径

| 步 | 动作 | 实测 |
|---|---|---|
| 1 | 点顶栏 `放置` | 菜单 25 项 |
| 2 | **悬停** `快捷器件(F)` | 右侧浮出子菜单：`电阻(R)` / `电容(C)` / `电感(I)` / `二极管(D)` |
| 3 | 点 `电阻(R)` | 进入放置模式，元件随光标 |
| 4 | 在画布空白处点一下 | 元件落下 |
| 5 | `Esc` | 退出放置模式 |

### 放下后读到了什么（C5 证据）

右侧属性面板从「图页」切换成「元件」，`选中数量 1`，字段：

| 字段 | 实测值 |
|---|---|
| 名称 | `=${值}`（默认取值的表达式） |
| ID | `$112` |
| 位号 | `R1`（已勾选） |
| 唯一ID | 有值 |
| 器件 | `Res...` |
| 封装 | `R0603` |
| 加入BOM | 是 |
| 转到PCB | 是 |
| PCB层 | 默认 |
| 关键属性 值 | `10K` |

所以「快捷器件」放出来的是**带默认值（10K）和默认封装（R0603）的通用电阻**，不用连网、不依赖立创编号。画 RC 振荡器够用，成本最低。

### 子菜单探测的坑（第二次踩）

`快捷器件(F)` 的子菜单必须**悬停**才出，且此时页面同时存在 3 个弹层：

```text
[333,27,253,688] 放置主菜单
[573,54,151,113] 快捷器件子菜单
[419,31,398,32]  工具栏悬浮提示
```

按「最大面积」或「最上层」都会拿回主菜单。唯一可靠的判据是**取 left 最大的那个**（573 > 333 > 419 里 573 最大且是唯一在父菜单右侧的）。

`menus` 探针目前只返回一个弹层，这条要改：返回全部弹层，由调用方按 left 选。

### 画布缩放与坐标

落点用屏幕坐标点击即可，不需要换算图纸坐标。底部状态栏有 `X / Y / dX / dY` 实时读数，可作为放置位置的粗校验，但不要依赖它做精确布局。

### 导线：能画出来，但还没证明连上

`Alt+W` 进入布线模式，两次点击（起点、终点）后生成一根导线，`Esc` 退出。

生成后右侧属性面板切到**导线**：

| 字段 | 实测值 |
|---|---|
| 名称 | `$1N1` |
| ID | `$1N1` |
| 全局网络名 | `$1N1` |
| 颜色 / 线宽 / 线型 | `#008E…` / 1（默认）/ 实线（默认） |

**未验证**：导线端点是否吸附到了元件引脚。证据是网络名仍是自动生成的 `$1N1`——如果两端真的落在引脚上，通常会并入已有网络名。当前这根线很可能是浮在画布上的独立线段。

要确认，必须用机器可读的手段：

1. `设计 → 检查DRC` 或底部 `DRC` 标签，看有没有「引脚未连接」类报错
2. 网络表/网络标签面板，看网络数是否因连线变化
3. 放大画布，观察端点是否出现连接圆点

### 坐标系的问题

放置与连线都用**屏幕坐标**，不换算图纸坐标。实测两次放置的落点与预期位置一致，但引脚位置只能靠估计，吸附是否成功肉眼难辨。所以「画上去」和「连上了」是两件事，前者已验证，后者未验证。

### 下一步

1. 用 `Alt+W`（导线）把两个元件连起来，确认连线同样只是「进入模式 + 坐标点击」
2. 连成后读属性面板或网络表确认网络成立
3. 再谈完整振荡器、PCB、铺铜、DRC

## 画布坐标映射、选中与旋转、画布出图

### 一、屏幕坐标 ↔ 文档坐标（关键基建）

文档坐标单位是 10 mil。屏幕坐标与文档坐标是线性关系，可以用 `sch_SelectControl.getCurrentMousePosition()` 现场标定，不必猜缩放。

实测（42% 缩放）：

| 屏幕 | 文档 |
|---|---|
| (400,300) | (43.88, 501.52) |
| (600,400) | (524.88, 261.02) |
| (500,250) | (284.38, 621.77) |

推导：

```text
比例 = 481.0 / 200 = 2.405  文档单位 / 屏幕像素
x 轴正向一致，y 轴反向

doc_x = 43.88 + (sx - 400) * 2.405
doc_y = 501.52 - (sy - 300) * 2.405

sx = 400 + (doc_x - 43.88) / 2.405
sy = 300 - (doc_y - 501.52) / 2.405
```

用法：鼠标移到两个已知点各读一次 `getCurrentMousePosition`，解出比例与偏移；之后任意文档坐标都能换算成可点击的屏幕坐标。缩放一变就重新标定。

### 二、选中与取消选中

```js
await A.sch_SelectControl.doSelectPrimitives(["<primitiveId>"]);   // 选中
var sel = await A.sch_SelectControl.getAllSelectedPrimitives();     // 读选中，返回数组
await A.sch_SelectControl.clearSelected();                          // 取消
```

也可以按映射后的屏幕坐标直接点选，实测能选中 `Component`。

### 三、空格旋转（选中状态下）

选中元件后发空格，`rotation` 0 → 90，**引脚坐标随之变化**：

| 状态 | pin1 | pin2 |
|---|---|---|
| 旋转 0° | (180,510) | (220,510) |
| 旋转 90° | (200,490) | (200,530) |

前提：**画布必须持有焦点**。没有焦点时空格无效（和 Esc 是同一个问题）。先用映射坐标点一下画布，再发键。

复原用 `modify(id, {rotation:0})`，比再按空格可预测。

### 四、画布出图（最适合视觉校验）

```js
var blob = await A.dmt_EditorControl.getCurrentRenderedAreaImage();
var dataUrl = await new Promise(res => {
  var fr = new FileReader();
  fr.onload = () => res(fr.result);
  fr.readAsDataURL(blob);
});
```

返回 **Blob**，转 dataURL 后就是 PNG（实测约 98 KB，131 KB base64）。

优点：**只有画布内容**，没有工具栏、面板、账号信息，比整页截图干净得多，适合直接做视觉判断与外发。

### 五、踩到的坑：移动元件会拉断已有导线

导线是一组固定坐标的图元，**不会跟随元件移动**。

实测顺序：R1 pin2 与 C1 pin1 之间建了 L 形导线 → 之后 `modify` 把 C1 从 y=590 挪到 y=700 → 画布图上立刻看到导线末端悬在半空，与引脚之间明显断开。

规则：**先定位置，再连线**。若必须移动元件，移动后要按新引脚坐标重建该网络相关导线，或直接重新走线。

判断是否断开，最快的办法就是出图看一眼（上一条），配合 `getAllPinsByPrimitiveId` + `getAll()` 的坐标对比。

### 六、一条完整的可靠链路

```text
1. 标定     鼠标两点 → getCurrentMousePosition → 比例与偏移
2. 放置     快捷器件菜单 + 映射后点击（或复用已有元件）
3. 定位     getAll → 找 designator → modify 到精确坐标
4. 旋转     modify({rotation}) 或 选中后空格
5. 取引脚   getAllPinsByPrimitiveId → 绝对坐标
6. 连线     sch_PrimitiveWire.create(折线, net) + await done()
7. 校验     出图看视觉 + 读回引脚与导线坐标
8. 清理     delete([ids])，及时删测试图元
```

这套链路里，只有第 2 步依赖鼠标，其余全部走 API，可重复、可断言。

## 进度条看门狗：卡住的识别与取消

### 现象

底部进度条停在 66%，持续 12 秒以上不动。渲染进程仍然响应（`Runtime.evaluate("1+1")` 立即返回），也没有模态框——所以不是线程卡死，是**某个 UI 任务没有收尾**。

### 复用的选择器

| 元素 | 选择器 | 实测 |
|---|---|---|
| 进度条容器 | `[class*="progress-message"]` | 文本即百分比（如 `66%`），高度 13px |
| 取消按钮 | `[class*="progress-tool-close"]` | 右下角 12×12，中心约 (1275, 714) |
| 进度整体 | `.progress_pS--j` | 1285×14，贴底 |

百分比文本在 `progressbar-text_GbWjM` 与 `progressbar-value-text` 两处都能读到。

### 看门狗规则

```text
1. 每 2 秒读一次 [class*="progress-message"] 的文本
2. 连续 3 次（约 6 秒）完全相同且非空 → 判定卡住
3. 点 [class*="progress-tool-close"] 的中心
4. 复查进度条消失（返回 none）
5. 立刻回读关键图元数量，确认数据没被写坏
```

阈值取 6 秒：正常操作（自动布线 1.4 秒、单次重建铺铜约 2—3 秒）都在 5 秒内收尾。

### 本次事故复盘

| 项 | 内容 |
|---|---|
| 卡住值 | 66% |
| 持续 | 12 秒以上（6 次采样全同） |
| 取消方式 | 点 (1275,714) |
| 取消后 | 进度条消失，数据完好 |

取消后的图元清点：6 元件 / 12 段走线 / 2 个铺铜（层 2 与层 1）/ 2 个灌注 / 6 个过孔 / 1 个板框，**DRC 仍为 0**。

**疑似诱因**：一次性 `pcb_PrimitivePour.delete([四个 id])`。批量删除铺铜会触发大范围重算与重灌注，数据改完了但进度条没走完。教训是——批量删除铺铜要么拆成单个删，要么删完主动等进度条收敛，不要立刻接下一步操作。

### 顺带修掉的一个隐患

「重建铺铜区」按钮的坐标会随属性面板内容漂移（y=499 与 y=461 都出现过）。之前写死坐标导致点击落空、误判为「按钮无效」。

正确做法：每次按文本 `重建铺铜区` 定位元素，取 `getBoundingClientRect()` 的中心再点。同理适用于任何面板按钮。

### 视觉确认

取消后截图：板框闭合、顶层铜皮已灌满（红色大区）、三只电阻三只电容在位、走线在铜皮下可见、四角与中点的过孔可见、底部 DRC 面板显示 `全部 (0)`、缩放 353%。

## 缩放有了，点击却是死的：新窗口输入通路排查

### 一、滚轮缩放可用（解决了放大问题）

`Input.dispatchMouseEvent` 的 `mouseWheel` 有效：

```js
s.call("Input.dispatchMouseEvent", {"type":"mouseWheel","x":600,"y":320,"deltaX":0,"deltaY":-120});
// 4 次后：比例 10.6 → 1.6 单位/像素（约 6.6 倍）
```

对比：`dmt_EditorControl.zoom()` 是 `return false` 的空实现；`zoomToRegion(l,r,t,b)` 调完比例不变。

**结论：要缩放就用滚轮事件，不要用 API。**

放大后焊盘直径约 37 像素，精度不再是问题（此前 6 像素确实点不准）。

### 二、但点击在这个窗口完全不生效

逐项验证：

| 动作 | 结果 |
|---|---|
| `focusWindow()` | 调用后鼠标位置开始更新 ✓ |
| 移动鼠标 | `getCurrentMousePosition()` 精确返回 (2000,−2000)，正是焊盘中心 ✓ |
| 滚轮 | 缩放生效 ✓ |
| 点击焊盘 | 选中数 0 ✗ |
| 9 点偏移扫描（±6px） | 全部 0 ✗ |
| `pointerType:"pen"` | 仍然 0 ✗ |
| 单路布线 后点击 | 不出线 ✗ |
| 差分对布线 后点击 | 不出线、无 toast ✗ |

模型侧是好的：`pcb_Document.getPrimitiveAtPoint(2000,-2000)` 正确返回该焊盘（`net: D_P`）。

`document.hasFocus()` 为 `true`，`elementFromPoint(812,188)` 命中的是 `IFRAME.editframe.un_ruler`（画布 iframe，非独立 target，同进程）。

### 三、判断

**鼠标移动与滚轮能到达画布，但按下/抬起不生效**。这不是坐标问题（位置读数正好落在焊盘中心），也不是遮挡问题（无覆盖层）。

对照实验：在 usb_hub 那个窗口里，同样的点击手法能触发提示（「检测到导线违反 DRC」），说明输入通路本身可用——**问题只出现在这个新开的工程窗口**。

可疑点：该窗口是双击工程树新建的，聚焦状态与常规窗口不同；`focusWindow()` 只把它提到前台，可能没有真正激活输入。

### 四、下一步可选项

1. 关掉这个窗口，重新从工程树双击打开（换个窗口实例再试）
2. 回到 usb_hub 窗口做布线（那里点击有效），但需先处理 7 条板框间距错误
3. 接受「定义可编程、布线需人工」这个边界，把两侧证据都写进文档

### 五、本轮净收获

- 滚轮缩放 = 唯一可用的缩放手段（已测量、已写死参数）
- 焊盘 `net` 传名即建网络（造差分网络的最短路径）
- 差分对定义全流程可脚本化（React props 点击 + 勾选 + 两级确认）
- 布线卡在「新窗口不接收按下/抬起事件」这一层，与之前的 DRC 门禁是两个独立问题

## 缩放键位的正解：I / O / K（不是 Ctrl+±）

用户指出我理解错了：说的是 **Ctrl 加加减号**；同时提示去查已爬的快捷键清单。

### 一、清单里有什么

`notes/_raw-shortcuts.json`（174 条）中与视图相关的条目：

| 功能 | 键 |
|---|---|
| 视图菜单 | `V` |
| 适应全部 | `K` |
| 全屏 | `F11` |
| 视图向左/右/上/下滚动 | `←` `→` `↑` `↓` |
| 根据光标位置居中视图 | `Shift+Home` |
| 切换图层亮度 | `Shift+S` |
| 翻转板子 | `Alt+F` |
| 单位 | `Q` |

**没有「放大 / 缩小」条目**——所以 Ctrl+= / Ctrl+- 无响应是符合预期的，那条路本来就不存在。

### 二、真正的缩放项藏在视图菜单里

按 `V` 打开视图菜单，第一行就是：

```text
2D预览 3D预览 3D外壳预览...
放大(I)  缩小(O)  适应全部(F) K  适应选中(E)  适应框选(A)  适应板框
全屏 F11  轮廓视图  显示颜色...  切换亮度 Shift+S  翻转板子 Alt+F  单位 Q
```

**缩放是单键 `I`（放大）/ `O`（缩小）**，不是组合键。这条清单里没爬到，是菜单里才看到的。

### 三、实测结果（含不稳定现象）

| 试验 | 结果 |
|---|---|
| `K`（适应全部） | 生效：1.6 → 10.6 |
| `I` ×3 | 生效过一次：10.6 → 7.03（约每按一次 ×0.87…0.9） |
| `O` ×1 | 未观察到变化 |
| `Ctrl+=` / `Ctrl+-` | 无变化（确认不是这两个键） |
| 滚轮 `mouseWheel` | 稳定生效：10.6 → 1.6（4 格） |

`K` 前后两次读数不同（10.6 与 7.03），说明**适配比例会随视图状态变化**，不能把 10.6 当常量。

### 四、为什么键盘时灵时不灵

这一版的根本问题还是**画布点击无效**：

- 鼠标移动 → 画布位置读数准确
- 滚轮 → 缩放生效
- 鼠标按下/抬起 → 完全不生效（选中数恒为 0，单路/差分对布线都不出线）

键盘快捷键只有在画布持有焦点时才响应，而"点一下画布"这条建立焦点的路刚好断了。所以按键表现成"有时生效、有时没反应"。

### 五、结论

1. 缩放键位：**`I` 放大 / `O` 缩小 / `K` 适应全部 / `V` 视图菜单**（记下来，别再猜 Ctrl±）
2. 缩放还有个稳定手段：滚轮 `mouseWheel`
3. 真正的拦路虎是"画布不接收点击"，它同时废掉了选择、布线、以及依赖点击建立焦点的键盘操作
4. 绕开办法：换一个窗口实例（重新双击工程树打开），或改用 usb_hub 窗口（那里点击是有效的）

## 「点击无效」的根因：我自己造成的两处错误

用户要求别绕、要找到原因。找到了，两条都不是软件问题。

### 一、事件探测器证明点击是通的

在画布 iframe（`iframe.editframe` → `document.title = "EasyEDA PCB"`）里挂捕获监听，再用 CDP 派发：

```text

mousedown   -> CANVAS @422,178
mouseup     -> CANVAS @422,178
click       -> CANVAS @422,178
```

事件完整到达画布 canvas，坐标也对。所以"点击不生效"根本不成立。

### 二、真正原因之一：坐标是缩放前的旧值

我算屏幕坐标时用的是当时比例（如 1.6 单位/像素），之后按了 `K`（适应全部）/`I`（放大），比例变成 4.4、7.0…… **旧坐标早就漂到空白处**，点击自然选不中。

### 三、真正原因之二：编辑器停在布线工具模式

之前多次尝试 `差分对布线`/`单路布线` 都失败了，但工具模式**没有退出**。在该模式下：

- 点击被工具吃掉（用于取起点/终点），不会触发选择
- 工具又在等一个"合法起点"，于是点哪都不动、还不报错

**按 2–3 次 `Esc` 退出工具后，同一次点击立刻 `selected = 1`。**

### 四、修复后单路布线成功

```text
Esc ×2 → 重新标定 → 布线 → 单路布线 → 点焊盘 → 拖到目标 → 点击 → Esc
结果：pcb_PrimitiveLine 总数 1，nets = ["D_P"]，长度 605 mil
```

这是"画布点击 + 布线路由"整条链路的第一个成功证据。

### 五、缩放键位（更正）

- 视图菜单（`V` 打开）里是 **`放大(I)` / `缩小(O)` / `适应全部(F)`（K）**，单键，不是组合键
- `Ctrl+=` / `Ctrl+-` **未绑定**，所以之前无反应符合预期
- 滚轮 `mouseWheel` 最稳：`deltaY:-120`，4 格约 6.6 倍
- **滚轮缩放以光标为中心** —— 要放大某处，先把鼠标移到那里再滚

### 六、仍卡住的一步：差分对布线

- 不弹提示（对比 usb_hub 那次会弹 DRC 提示）

2. 可能要先在 `差分对管理器` 里点「应用」把对"生效"（我们点的是确认，关闭了对话框）
3. 也可能它依赖已有走线的延续，而非从零起布

## 工具模式可观测性：光标路不通，总线里的 `tool` 通道可用一半

用户要求别靠猜，找实时信号判断"当前处于什么工具模式"。测了三条路。

### 一、CSS cursor：不可用

| 状态 | body.cursor | canvas.cursor |
|---|---|---|
| 空闲 | `default` | `default` |
| 单路布线中 | `default` | `default` |
| Esc 之后 | `default` | `default` |

全页面扫描也没有任何非 `auto/default` 的 cursor 元素。**EDA 不用 CSS cursor 表达工具状态**（大概率是 canvas 内部绘制或原生光标），这条路放弃。

### 二、消息总线 `tool` 通道：能报"进入"，不报"退出"

订阅 `MSG_BUS_PCB.*.subscribe('tool', cb)`：

```text
进入 布线 → 单路布线  → 收到 tool = "draw(track)"
按 Esc 退出            → 没有新的 tool 消息（只看到 keydown / updateFrame / updateModify）
```

所以：

- ✅ 能实时知道"刚进入了哪个工具"（值形如 `draw(track)`）
- ❌ **不能**知道"工具已经退出"——Esc 后 `tool` 值仍停在 `draw(track)`

单靠它做状态机，会在"已退出但值没变"上误判。

### 三、右侧面板切换：弱信号

进入工具后右侧面板从 `图层` 变成 `属性`（布线时出现「布线属性」分组）。这是真实可读的，但不能区分"选中对象"和"工具激活"，只能当辅助线索。

### 四、结论：检测不可靠，那就把状态"归零"再验证

既然没有可靠的实时模式读数，正确做法不是猜，而是**每次画布交互前把状态归零并验证**：

```text
1. Esc ×2–3                  （幂等，无论当前什么工具都退回选择态）
2. 重新标定坐标               （缩放变了旧坐标全废）
3. 试探点击一个已知焊盘       （selected ≥ 1 才算状态正常）
4. 再执行真正的操作
```

第 3 步是关键——**用一次无害的点击验证"当前点击会被当成选择"**，等于把不可观测的模式转换成了可观测的探针。

### 五、这条纪律已写入跨项目记忆

`~/.workbuddy/user-*/MEMORY.md` 新增「交互自动化的坐标与模式纪律」：

- 坐标现读现用，跨步骤复用必点空
- 视图变化（缩放/滚动/尺寸）后坐标全部作废
- 画布交互前先 Esc 归位
- 判断"点击无效"的顺序：事件监听 → 遮挡检查 → 坐标新鲜度 → 工具模式

同一条纪律此前在"点按钮"上已经犯过一次，这次在画布焊盘上又犯一次，所以落到全局。

### 六、附带结论：缩放

- 键位：视图菜单里是 `I`（放大）/ `O`（缩小）/ `K`（适应全部），单键
- `Ctrl+=` / `Ctrl+-` 未绑定
- 滚轮 `mouseWheel(deltaY:-120)` 最稳，且**以光标位置为缩放中心**——要放大哪里就把鼠标放哪里再滚

### 一、无侵入输入：已验证可用

document.querySelector('iframe.editframe').contentWindow.focus();

| 鼠标移动 → 标定 | 两点差 (90, −50)，比例 **0.6 单位/像素** ✓ |

## 坐标校验的三个陷阱（都是"看起来像坐标错了"）

### 一、光标移出画布后，`getCurrentMousePosition()` 会冻结

```text
(950, 450) → (5440.0, -7385.5)   画布内，正常
(1100, 300) → (5440.0, -7385.5)  落在右侧面板上，读数原封不动
```

不报错、不返回 null，就是**一直返回最后一个画布内坐标**。
后果：校验时算出"映射误差 190 mil / 810 mil"这类吓人的数字，其实是落点出界。

修法：校验前先拿 `iframe.editframe` 的 `getBoundingClientRect()`，落点不在框内直接判失败。

```js
var f = document.querySelector('iframe.editframe'), r = f.getBoundingClientRect();
// rc = [left, top, right, bottom]
```

### 二、状态栏 / 属性面板的 X、Y 是**相对板框原点**

同一焊盘三处读数：

| 来源 | X | Y |
|---|---|---|
| API `getCurrentMousePosition` / `pcb_PrimitivePad` | 4916.9 | -6825.5 |
| 状态栏 | 895 | -3485 |
| 属性面板「中心X / 中心Y」 | 896.9 | -3485 |

差值恒定 `(4020, -3340)` = 板框左下角。**别拿状态栏校验 API 坐标**。
（反过来有用：想知道板框原点，用这个差值反推。）

### 三、标定不能用"两点定比例"

- 画布吸附网格（本例 5 mil），单个采样点可能被吸走一格；
- X/Y 实测比例会差 1%（2.6667 vs 2.690），强行共用一个比例会把有效解判成残差超限。

正确做法：两轴各自最小二乘

```text
docX = bx + sx * scrX
docY = by + sy * scrY
```

用 6 个分散采样点拟合，超出容差的点剔除后重拟合，残差 ≤8 mil 才算成功。
实测稳定产出 `残差 1.58~2.48 mil，XY 偏差 0.09%~0.12%`。

### 四、点击"焊盘中心"为什么选不中：两个几何事实

曾观察到同一坐标在不同缩放下命中结果不一致（0.601 命中 / 0.953 不命中 / 1.527 命中），
一度归因为"焊盘太小、命中判定随像素变化"。**这个归因是错的**，用
`pcb_Document.getPrimitiveAtPoint` 直接查命中后就清楚了：

**事实一：焊盘中心常常被自家走线端点占住。**

```text
getPrimitiveAtPoint(4916.9, -7025.5) → Line e103  net=VCC18  起点 (4916.909,-7025.5) → (4885,-7025.5)
```

线的起点正是焊盘中心。U1 每个引脚都有一条这样的既有走线，所以：

```text
沿 x 扫描 D_P 焊盘（y=-6825.5）：
x=4900..4918 → Line:D_P      ← 走线覆盖
x=4921..4936 → Pad:D_P       ← 焊盘本体
```

点中心 → 命中的是线 → 选中的是**整条网络**（D_P 实测 13 段），不是焊盘。

**事实二：焊盘坐标不一定在图形上。**

A6 焊盘 `(4598,-6970.7)` 命中 `null`，左右 ±15mil 才是 `Pad`——焊盘实体分成两块，
坐标落在中间的缝上。5×5 采样：

```text
dy=+30  Comp | Comp   | Comp | Comp   | EXC
dy=+15  Comp | Pad:D_N| null | Pad:D_N| EXC
dy=  0  Comp | Pad:D_P| null | Pad:D_P| EXC
dy=-15  Comp | Pad:D_N| null | Line:D_N| EXC
dy=-30  Comp | Comp   | null | Comp   | EXC
```

当初"随缩放变化"的非单调结果，是每次重新标定带来的 1–2 像素落点漂移，
在这个只有几像素宽的目标上刚好跨过/没跨过走线边缘——**噪声，不是机制**。

结论：不要用"点焊盘看选中几个"判断坐标对不对。用命中查询（见下节）先问清
"这一点最上面是谁"，再决定点哪里。

### 五、命中查询：`pcb_Document.getPrimitiveAtPoint(x, y)`

```js
await A.pcb_Document.getPrimitiveAtPoint(4916.9, -6825.5)
// → Pad / Line / Component / Via / null（最上面一个，含 primitiveId 与 net）
```

| 项 | 说明 |
|---|---|
| 返回值 | 只给**最上面一个**（封装层 `return r[0]`，底层 rpc 其实返回数组） |
| 命中 Polygon/铺铜 | 抛 `单多边形验证不通过`（封装 bug：`pathString` 被包成数组）→ 必须 try/catch |
| 瞬时空结果 | 画布重绘时会返回空数组 → 重试一次；同坐标连续 8 次查询本身稳定 |
| 原理图 | 同名接口 `sch_Document.getPrimitiveAtPoint` |

用法：**在焊盘附近采样，挑一处"最上面就是目标焊盘"的点再点**。采样步长必须大于
压在焊盘上的走线半宽——用短边 1/4（5.5mil）时 8 个采样点全落在线上，会得出
"焊盘不可命中"的错误结论；改短边 1/3 起（下限 6mil）就正常。

```text
命中采样: +0,+0→Line  +7.3,+0→Pad  -7.3,+0→Line  ±14.7→Component  对角→Pad
点击点: [4924.2, -6825.5] → Pad:D_P
```

注意：**布线起点仍要用焊盘中心坐标**（布线器自己会吸附），偏移点只用于"需要点击
命中焊盘"的场合——用偏移点起布会让落线起点偏 7mil 左右，端点校验判不过。

### 六、探针规范

| 断言目标 | 手段 | 为什么 |
|---|---|---|
| 焊盘存在且可选中 | `clearSelected` → `doSelectPrimitives([primitiveId])` → 回读 ids | 与点击无关，100% 确定 |
| 该点点击会命中谁 | `getPrimitiveAtPoint(x, y)` | 应用自己的命中判定，可离屏任意采样 |
| 点击能落到画布并完成选择 | 点**屏幕上**一条导线中点，期望选中 ≥1 个（落在整网时是 9~13 段） | 导线不会像焊盘那样命中到别的东西，选中数不含糊 |
| 坐标映射正确 | `getCurrentMousePosition` 回读 + 画布边界预判 | 直接反映画布自己认的坐标 |

| 变体 | 落线 | 结论 |
|---|---|---|
| 对照：不动 | +2 段 | 判据有效，工具确实在画 |
| Esc ×1（焦点在 iframe） | +2 段 | 工具仍激活 |
| Esc ×2（焦点在 iframe） | +2 段 | 工具仍激活 |
| **右键 ×1** | 0 段 | **工具已退出** |

视觉侧一致：工具态有贯穿画布的十字准线；右键后退回选择态（准线消失、悬停弹出元件信息浮窗）。

### Esc 为什么靠不住

```text
iframe 内 keydown 监听 → 收到 Esc / I / O / Q → 事件确实进了 iframe DOM
同一路径按 Q → 单位 mil→mm→mil → 快捷键链路本身是通的
同一路径按 I / O → 视图比例不变 → 应用不响应
同一路径按 Esc → 工具不退、连右键菜单都关不掉
```

即：不是"按得不够多"，也不是"键盘注入失败"，而是 Esc / 缩放这类键的响应层
与 CDP 注入的事件不在同一层（Q 这类编辑器级快捷键能响应）。具体在哪一层未定位。

### 右键有两种后果，要分开处理

| 场景 | 右键后 |
|---|---|
| 工具激活 | 直接退工具，**不弹菜单** |
| 选择态 | 弹右键菜单 `.ctxmenu-ulist`（实测 202×377） |

菜单关闭方式：

| 方式 | 结果 |
|---|---|
| 再右键一次 | 菜单还在 |
| Esc ×1 | 菜单还在 |
| **点画布空白** | 菜单消失 ✓ |

点空白关菜单不产生副作用：线段数不变、不留图元、不落线。

### 归零流程

```text
1. 右键（画布中心或已知空白处）      → 退工具
2. 检查 .ctxmenu-ulist 是否可见      → 可见就点画布空白关掉
3. 补一次 focus + Esc                → 兜底，不作为主要手段
4. 重新标定坐标                      → 退工具/关菜单都可能改变视图
```

判据设计教训：**对照组必须能跑出正结果**。对照都不落线时，任何"变体无变化"都不算证据。
