# 启停脚本与常驻入口

连接层与主流程见 `SKILL.md`。本篇只讲实例生命周期：怎么把「带端口启动」变成一条可重复执行的命令，以及要不要让它常驻。

## 一、生成启停脚本

手动敲一长串参数启动，每次都要重来；放在助手会话里跑，又会被回收。所以收尾时给用户生成一份启停脚本，让他自己管实例生命周期。

先问清输出目录，再用 dry-run 确认写入位置：

```bash
python scripts/render_launcher.py --out-dir <目录> --dry-run
```

确认后正式生成（端口默认 9222，`--port 0` 表示动态端口）：

```bash
python scripts/render_launcher.py --out-dir <目录>
```

自动探测不到客户端时加 `--exe <主程序完整路径>`；要给另一台机器生成时加 `--target windows|macos|linux`。

产物：

| 目标平台 | 文件 |
|---|---|
| Windows | `lceda-cdp.ps1`、`lceda-cdp.cmd` |
| macOS / Linux | `lceda-cdp.sh` |

统一五个动作：`start`、`ensure`、`status`、`endpoint`、`stop`。

`start` 会先看有没有别的客户端进程在跑：客户端是单实例的，已有实例在运行时新启动的参数会被转交后丢弃，端口根本不会开。确实要并行开第二个时加 `-Force`（Windows）或 `-f`（macOS / Linux），但两个实例会争抢同一份数据，只在排查时这么干。

`start` **默认清掉进程级代理环境变量**再拉起客户端，理由见下一节。要沿用它们时加 `-KeepProxyEnv`（macOS / Linux 是 `--keep-proxy-env`）。

`ensure` 是自愈入口：没进程就按 `start` 起，有进程就等端点，等不到再按「命令行带不带调试端口」分别给处置。它**永远不会杀进程**——那会丢未保存的工程。

## 一之一、为什么要清代理环境变量

Chromium 的代理优先级是：**命令行开关 > 代理环境变量 > 系统代理**。只要 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` 里有一个非空，客户端就完全不理 Windows 的「系统代理」设置。

而这些变量通常不是用户设的，是某个终端或工具临时注进环境的（实测：助手会话里是 `127.0.0.1:25133` 的沙箱代理，只对那个终端及其子进程有效）。从这个环境里拉起客户端，它就会去连一个只给那个终端开的代理：

- 冷启动并发十几个 API/图片请求，全部连不上，每个都挂到 TCP 超时（实测 ~80 秒、`transferSize=0`）
- 用户看到的是「窗口三十秒不出来 + 出来以后白屏 + 提示网络异常」
- 和「网络真的断了」长得一模一样，极难自查

所以默认清掉，让客户端回到「按系统代理走」这条唯一可解释的路径。清理范围是 `http_proxy` / `https_proxy` / `all_proxy` / `ftp_proxy` / `no_proxy` 的大小写全部形态（Windows 上不区分大小写，实际会把 `HTTP_PROXY` 与 `http_proxy` 一起清）。`start` 会把清掉的变量逐条打印出来，便于核对。

要显式指定代理（比如系统代理还没生效的启动窗口期），用 `-ProxyServer http://127.0.0.1:7897`，它对应 Chromium 的 `--proxy-server`，优先级高于环境变量。

## 二、脚本自己保证的安全边界（不要绕过）

- 只停自己启动的那个实例：进程号记在同目录 pid 文件里，停止前校验镜像路径，防 PID 复用误杀。
- `stop` 必须显式确认（`-Yes` 或 `-y`），因为杀进程会丢未保存的工程。
- 不自动强杀。进程不理会正常终止时只报告，让用户在客户端里自己退出。
- 不碰用户的其它实例，也不删任何数据。

## 三、交付话术

两件事必须说清：

1. 脚本里嵌了本机安装路径，属于本地信息，**别提交到公开仓库**。
2. 换机器或换端口就重新生成，不要手改脚本。

**让用户自己跑，不要代跑。** 脚本生成完，把路径和命令交给用户，由他在自己的终端里执行。从助手会话里代为启动，进程仍可能随会话回收，白折腾一次。

终端上出现「走的是兼容启动路径」的提示时，说明当前环境的 PowerShell 启动器有环境变量冲突、退到了备用路径，客户端的 stderr 会直接打在屏幕上。不影响连接，端点照样能起来。脚本控制台里夹带的 `libDirs` 之类客户端日志同理，忽略即可。

## 四、要不要常驻

走到这一步说明每次都得靠脚本启动。接着问用户一句：要不要让日常双击也能带 CDP。

问之前先把事实说清，别让用户以为改个配置就行：

**配置文件里没有能开启 CDP 端口的开关。** `config.json` 的 `devTools` 只会在启动后打开本地 DevTools 窗口，既不监听端口，也不产生 `DevToolsActivePort`（设成 `detach` 实测：0 个监听，无端口文件）。所以「改配置就常驻」这条路不存在。

能持久化的只有让启动过程带上参数：

| 方案 | 做法 | 代价 |
|---|---|---|
| 开始菜单入口 | `--install-startmenu` | 不改安装文件，升级不受影响，一条命令可删 |
| 指向启停脚本的快捷方式 | 用户手动把图标指向脚本 | 同上，但占掉一个图标位 |
| 改 `app.js` 注入开关 | 用户自行决定 | 改安装文件、每次升级失效、调试端口长期敞开；本 skill 不代做，也不宣称可行 |

```bash
python scripts/persist_cdp.py --probe                # 先看现状
python scripts/persist_cdp.py --install-startmenu    # 装入口
python scripts/persist_cdp.py --remove-startmenu     # 卸载
```

入口默认调用 `~/.lceda-cdp/lceda-cdp.ps1`，所以启停脚本必须先存在；放在别处时用 `--launcher` 指定。

用户明确拒绝就跳过这一步，继续按脚本启动。**不要擅自安装**：这是往用户的开始菜单里写东西，属于改变本地状态，要先得到同意。

## 五、客户端自己会重启

设置里改运行模式、清缓存、导入激活文件、客户端升级——这些都会让客户端自己退出再拉起，端点可能就没了。哪些入口会重启、重启后启动参数还在不在、失效的现场怎么重建，见 `@references/restart-and-relaunch.md`。

只记一条最要紧的：**`--remote-debugging-port` 必须排在启动参数的第一位**。客户端「清理缓存」那条重启通道只把 `process.argv[1]` 传给新进程，端口排在后面就会在自重启后丢掉。脚本里已经按这个顺序写死，不要重排。
